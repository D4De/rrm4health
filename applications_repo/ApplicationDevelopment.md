# Application development tutorial

This guide explains how to integrate a Python application into RRM4Health:
write its JSON descriptor, generate a class skeleton, implement its tasks,
and launch it through the framework.

For installation and a complete BreathAnalysis demo using the WebApp, RRM Global
and RRM Local, start with [HowToStart](../HowToStart.md). For firmware changes,
see [Adding IMU features](../utilities_library/AddingImuFeatures.md).

All shell commands below run from the repository root (the directory containing
`framework/` and `applications_repo/`), unless explicitly stated otherwise.

## 1. Find the right reference

The main examples and integration helpers are:

```text
utilities_library/
├── BleAcquisitionMngr.py
├── WifiAcquisitionMngr.py
├── FileAcquisitionMngr.py
├── MqttTransmissionMngr.py
├── ExampleAllMngr.py
├── TestBleAcquisitionMngr.py
└── TestWifiAcquisitionMngr.py
```

The shared managers and executable integration examples live in
`utilities_library/`; new integrations should use these PascalCase modules and
classes. Board firmware lives in `imu/`, and development tools in `tools/`.

The naming rule applies to both files and classes: `BleAcquisitionMngr.py`
defines `BleAcquisitionMngr`, `WifiAcquisitionMngr.py` defines
`WifiAcquisitionMngr`, `FileAcquisitionMngr.py` defines `FileAcquisitionMngr`,
and `MqttTransmissionMngr.py` defines `MqttTransmissionMngr`. The import
examples below use these exact names.

Deployed applications live in
[`framework/applications/`](../framework/applications/), and their registered
descriptors directly in that same directory, outside the individual application
folders (for example, `framework/applications/BreathAnalysis.json`).
Editing an example does not automatically update its deployed copy.

[ExampleAllMngr.py](../utilities_library/ExampleAllMngr.py) illustrates acquisition, processing and publication.
Despite its class name `BreathAnalysis`, its processing is a generic demonstration,
not the production respiratory-analysis algorithm. For that algorithm, use the
[deployed BreathAnalysis application](../framework/applications/BreathAnalysis/BreathAnalysis.py)
and its [descriptor](../framework/applications/BreathAnalysis.json).

## 2. Prepare the Python environment

Use Python 3.10 or newer and a virtual environment:

```bash
python3 -m venv venv
source venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt jsonschema
```

Install additional dependencies for the application you are developing, for example:

```bash
python -m pip install -r framework/applications/BreathAnalysis/requirements.txt
```

Keep an application-specific `requirements.txt` beside your application's Python
file. RRM Local prepares application environments from these requirements; cover
all third-party imports used by the application and its helpers.
See [HowToStart](../HowToStart.md) for system dependencies and startup commands.

## 3. Write the descriptor

Create `applications_repo/WindowDemo/` and save the following descriptor there
as `WindowDemo.json`. This
minimal application produces a synthetic window, calculates its mean and prints
the result; no IMU or MQTT broker is needed.

```json
{
  "name": "WindowDemo",
  "taskgraph": [
    {
      "id": "Acquire",
      "description": "Produce a synthetic data window",
      "depends_on": [],
      "input": [],
      "output": ["window"]
    },
    {
      "id": "Processing",
      "description": "Calculate the mean of the window",
      "depends_on": ["Acquire"],
      "input": ["window"],
      "output": ["result"]
    },
    {
      "id": "Save",
      "description": "Print the processing result",
      "depends_on": ["Processing"],
      "input": ["result"],
      "output": []
    }
  ],
  "executable": {
    "path": "applications/WindowDemo/WindowDemo.py",
    "parameters": {
      "campaignname": "demo"
    },
    "timeouts": {
      "setup": 60,
      "loop": 5,
      "cleanup": 10
    }
  },
  "configurations": [
    {
      "id": "single_node",
      "partitions": [
        {
          "id": "partitionA",
          "tasks": ["Acquire", "Processing", "Save"],
          "node": "{{NODE_A}}",
          "required_resources": {
            "ram": 128,
            "disk": 128,
            "network_upload": 0,
            "network_download": 0
          }
        }
      ],
      "channels": []
    }
  ]
}
```

### Descriptor rules

- `name` identifies the Python class generated by the creator. Choose a valid
  Python identifier, and use valid identifiers for task IDs and input/output names.
- `taskgraph` is a list at the document root. `executable` and `configurations`
  are separate root fields, not children of `taskgraph`.
- `depends_on` defines dependencies. `input` names become arguments of
  `<task_id>_loop`; `output` names become the keys it returns.
- `executable.path` is relative to `framework/`, not to `applications_repo/`.
- `executable.parameters` contains flat values: `"{{hint}}"` marks a required
  user parameter, an ordinary string supplies a default, and an empty string
  marks an optional value. Read them through `self._user_args`. Do not add
  framework-managed parameters such as `Ind_conf` to this dictionary.
- `timeouts` supplies setup, loop and cleanup budgets in seconds. Keep blocking
  operations bounded and compatible with these budgets.
- Each configuration assigns tasks to partitions and nodes. Select the target
  for `{{NODE_A}}` through the launch interface. Declare channels for
  cross-partition dependencies using `from_partition` and `to_partition`.

For example, if acquisition runs in `partitionA` and processing in `partitionB`,
the channel entry is `{"from_partition": "partitionA", "to_partition": "partitionB"}`.
Do not reuse the old channel format with manually configured socket ports.

For physical sensors, describe the resource request in the acquisition task's
`requires` list. This entry requests three exclusive BLE IMUs and links their
selected IDs to the executable parameter `imunames`:

```json
{
  "type": "ResourceRequest",
  "count": 3,
  "exclusive": true,
  "parameter_linked": "imunames",
  "separator": "-",
  "features": {
    "gyro": {},
    "acc": {},
    "magn": {},
    "ble": {}
  }
}
```

This fragment is not a complete descriptor: add `imunames` to
`executable.parameters` and place the entry inside the task's `requires` list.
For one requested device, use `count: 1` and an empty `separator`.
Capabilities and location constraints must match registered resources; do not
copy deployment-specific locations blindly.

## 4. Validate and generate the skeleton

Validate the descriptor:

```bash
PYTHONPATH=framework python tools/CheckerJSON.py applications_repo/WindowDemo/WindowDemo.json
```

Check that the output reports `VALID`. The checker takes a positional path;
`--manifest_name` belongs to the creator, not the checker.

Generate the class in its destination directory:

```bash
mkdir -p applications_repo/WindowDemo

cd applications_repo/WindowDemo
PYTHONPATH=../../framework python ../../tools/AppSkeletonCreator.py \
        --manifest_name WindowDemo.json

```

The creator writes `<descriptor name>.py` in the current working directory.
It generates task methods, not your algorithm. Run it only when creating the
application, or in a scratch directory when comparing a revised descriptor:
regenerating into the application directory overwrites the Python file.

## 5. Implement the generated methods

Keep `set_framework`, `setup`, `cleanup`, and all generated task methods.
For the descriptor above, fill in these methods inside the generated class:

```python
def Acquire_setup(self):
    self._next_sample = 0
    return True

def Acquire_loop(self):
    # Synthetic data for this tutorial; replace with your acquisition source.
    window = list(range(self._next_sample, self._next_sample + 10))
    self._next_sample += 10
    return {"window": window}

def Processing_loop(self, window):
    return {"result": sum(window) / len(window)}

def Save_loop(self, result):
    campaign = (self._user_args or {}).get("campaignname", "demo")
    print(f"{campaign}: mean={result}", flush=True)
    return {}
```

The lifecycle is:

1. Global `setup`, then task setup methods in dependency order.
2. Repeated task loop execution following the dependency graph.
3. Task cleanup in reverse dependency order, then global `cleanup`.

Use instance attributes for state that persists between iterations of the same
task. Pass data between tasks through returned dictionaries, not shared globals
or attributes: tasks can run in different processes or nodes.

Loop methods return a dictionary with consistent keys; a terminal task with no
output returns `{}`. The runtime also accepts `None`, but this does not
automatically skip downstream tasks. A consumer with required arguments may
then fail because its input keys are missing. For nonblocking acquisition, use
a stable envelope such as `{"window": None}` while waiting, and explicitly
handle that value in every consumer, propagating an empty result as needed.

Match output keys and consumer argument names exactly. Keys may be reused along
a chain or in separate branches, but two producers must not directly converge
into the same consumer with an ambiguous key. Do not assume an execution order
between independent tasks on the same dependency level.

Initialize resources in the owning task's setup and release them in its cleanup.
Cleanup should also tolerate a partially completed setup. Preserve global hooks
even if they do nothing. To stop intentionally, call
`self._app.stop_application()`; status updates use `self._app.send_status(status)`.

### Alternative: implement the methods and algorithm with AI

Instead of implementing the generated methods manually, you can ask an AI coding
assistant to integrate your existing single-file script into the skeleton. Use
the repository's [integration prompt](../tools/Prompt.txt) as the starting prompt.
The developer still writes the descriptor and generates the empty class first,
following sections 3 and 4: the AI fills in that structure, rather than deciding
the task graph on its own.

1. Prepare and validate your application's descriptor, then generate the skeleton
   in a new directory. Keep a copy of the original script and the empty skeleton
   so you can compare them with the integrated version.
2. Provide the IA with all of these files, as attachments:

   - Your JSON descriptor from `framework/applications/`.
   - The empty Python skeleton produced by `AppSkeletonCreator.py`.
   - The original single-file script containing the algorithm to integrate.
   - [ExampleAllMngr.py](../utilities_library/ExampleAllMngr.py), as a reference for manager integration, not as a
     replacement for your algorithm.
   - The manager implementations used by the example:
     [BleAcquisitionMngr.py](../utilities_library/BleAcquisitionMngr.py),
     [WifiAcquisitionMngr.py](../utilities_library/WifiAcquisitionMngr.py) and [MqttTransmissionMngr.py](../utilities_library/MqttTransmissionMngr.py).

3. Copy the contents of `promptForIA.txt` into your request. Adapt its
   **Richieste specifiche** section to your application before submitting it:
   the current text requests BLE-only acquisition, RAW mode and two MQTT streams
   (acquired data and processed results). Those are application choices, not
   universal framework requirements. If you need Wi-Fi or FEATURES, say so
   explicitly and keep the request consistent with your descriptor and algorithm.
   Prefer Wi-Fi for high transmission frequencies; BLE can be used for low ones.
4. Ask the assistant to identify incompatibilities and map original functions to
   tasks, methods, inputs, outputs and persistent state before implementing the
   integration. Keep the descriptor authoritative: task IDs, dependencies and
   method signatures must not change silently. Review and approve any proposed
   descriptor changes before applying them and regenerating a skeleton.
5. Review the generated application, imports, dependencies and any local manager
   adapters. Check that the original algorithm is preserved, parameters come from
   `self._user_args`, resources belong to the correct tasks, and cleanup releases
   them. If two MQTT streams are requested, verify that two separate manager
   instances publish acquired data and serialized processing results respectively.
6. Compare the integrated algorithm's output with the original script on
   the same known inputs. Test acquisition, missing data, timeouts and cleanup on
   a local node before distributing tasks. AI-generated code is not validated
   merely because it compiles; review the assistant's assumptions and unresolved
   issues before using real sensors or publishing to a live database.

The expected result is an implemented application with its required helpers and
dependencies, plus a summary of changes, required parameters, assumptions and
unresolved issues. This alternative changes who implements the methods, not the
framework's lifecycle or the validation requirements described above.

## 6. Integrate BLE, Wi-Fi or simulated acquisition

Use [ExampleAllMngr.py](../utilities_library/ExampleAllMngr.py) as an integration reference. Its implemented task
methods are `setup_and_collect`, `Processing` and `Save`; use these IDs in a
matching descriptor.

The example imports shared managers from `utilities_library`. Keep that package
alongside `framework/` on every execution node; AppStarter makes the repository
root importable.
See [the shared library guide](../utilities_library/README.md).

### Select the transport

Use these imports from a repository-root Python session or an application
launched by AppStarter:

```python
from utilities_library.BleAcquisitionMngr import BleAcquisitionMngr
from utilities_library.WifiAcquisitionMngr import WifiAcquisitionMngr

# For high transmission frequencies, prefer the Wi-Fi manager.
# For low transmission frequencies, BLE can be used.

# BLE configuration:
ble = BleAcquisitionMngr()
ble.set_imus(["IMU_A", "IMU_B"])
ble.set_id_imus(["thorax", "abdomen"])
ble.set_adapter("hci0")

# Wi-Fi configuration: one IP address or MAC address per IMU.
wifi = WifiAcquisitionMngr()
wifi.set_imus({
    "IMU_A": "AA:BB:CC:DD:EE:01",
    "IMU_B": "AA:BB:CC:DD:EE:02"
})
wifi.set_id_imus(["thorax", "abdomen"])
wifi.set_access_point("wlan0", "your_ssid", "your_password")
```

Typically `hci0` is the internal Bluetooth adapter and `hci1` an external USB
adapter; verify the actual enumeration on your machine. Wi-Fi MAC resolution
depends on the manager's DHCP lease configuration and the network.
See [TestWifiAcquisitionMngr.py](../utilities_library/TestWifiAcquisitionMngr.py) for the standalone test: it accepts
multiple MAC addresses separated by `-` (keep `:` inside each MAC).

### Select RAW or FEATURES

Both real managers accept the same campaign configuration:

```python
manager = ble  # Or wifi; configure and start only the selected manager.

# RAW: receive individual samples and build processing windows in Python.
manager.set_campaign("demo", 10, raw=True)

# Alternative FEATURES configuration (use this INSTEAD of the RAW call):
# Features are calculated on the IMU and sent once per window.
# manager.set_campaign(
#     "demo", 10, raw=False, window_size=300, step_size=100
# )

manager.start_collection()
try:
    manager.wait_connection()
    packet = manager.get_packet(block=True, timeout=0.1)
    if packet is not None:
        print(packet)
finally:
    manager.stop_collection()
```

In a framework application, split this lifecycle across the acquisition task's
setup, loop and cleanup rather than receiving only one packet as above. Keep
receive timeouts compatible with the loop budget and handle `None` when no
packet is available. Check packet types before building a sample window:
battery messages are not measurement samples.

RAW transmits every sample and generates more traffic. FEATURES requires
compatible firmware and transmits summaries instead of the original time series.
With 10 Hz sampling, a 300-sample feature window first completes after about
30 seconds; a 100-sample step produces a new window about every 10 seconds.
Sampling frequency and transmission frequency therefore differ in FEATURES mode.
Prefer Wi-Fi for high transmission rates; BLE can be used for lower rates,
subject to hardware and payload size.

Do not treat hexadecimal RAW values as already calibrated physical quantities.
Decode and scale them according to the sensor and firmware; feature packets
contain calculated numeric values. See the
[firmware guide](../utilities_library/AddingImuFeatures.md) for packet formats, feature
definitions and ESP32-C3 hardware notes.

### Replay files instead of connecting real IMUs

```python
from utilities_library.FileAcquisitionMngr import FileAcquisitionMngr

manager = FileAcquisitionMngr(input_dir="input", loop_files=True)
manager.set_imus(["IMU_A", "IMU_B"])
manager.set_id_imus(["thorax", "abdomen"])
manager.set_campaign("demo", 10, raw=True)
```

Use the same collection lifecycle shown above. With this `input_dir`, the simulator reads
`input/thorax.jsonl` and `input/abdomen.jsonl` relative to the working directory, named after the
configured IDs. It also accepts files without an extension and `.json`, `.csv`
and `.txt` files; see [the implementation](../utilities_library/FileAcquisitionMngr.py) for parsing
details. Without `input_dir`, files are read from `utilities_library/input/`.

The simulator paces file records at the configured frequency. It does not
calculate firmware features from RAW data: to replay FEATURES, provide feature
records. `loop_files=True` repeats the input; the default is `False`, which stops
replaying a device at end-of-file. Use a bounded receive timeout so exhausted
input files cannot block a task indefinitely.

## 7. Process a window and publish through a separate MQTT instance

The integration pattern in `ExampleAllMngr.py` is:

```text
acquisition → window/feature packets → Processing → result → Save
     └── acquisition MQTT instance                  └── result MQTT instance
```

Use two `MqttTransmissionMngr` instances: one for acquired data, another for processing
results. They can use different topics on the same broker, or different brokers
backed by different databases. The result publisher receives the processing
output, not the original acquisition packet again.

The manager API is:

```python
from utilities_library.MqttTransmissionMngr import MqttTransmissionMngr

output_mqtt = MqttTransmissionMngr()
output_mqtt.set_db_mqtt("localhost", 1883, "demo/results")
output_mqtt.start_db_mqtt()
try:
    # The project's MQTT ingestion uses comma-separated key=value fields.
    # Match the schema expected by the downstream consumer.
    output_mqtt.put_row("campaign=demo,imuid=thorax,mean=1.25")
finally:
    output_mqtt.stop_db_mqtt()
```

For distributed execution, create the acquisition publisher in the acquisition
task and the result publisher in the saving task. A publisher created only in
another partition's setup is not available through `self` on the saving node.

`put_row` queues an already serialized string; it does not convert a dictionary
to CSV. The comma-separated `key=value` convention is not a standard
header-and-values CSV file. Serialize explicitly and agree on escaping, field
names and types with the consumer.

MQTT is the transport, not the database itself. `host_DB` and `port_DB`.

## 8. Launch through the framework and configure presets

Check Python syntax before launching:

```bash
python -m py_compile applications_repo/WindowDemo/WindowDemo.py
```

Before launching a new application, install a reviewed copy of its directory
and descriptor using the [application repository guide](README.md).
Keep the source and descriptor together in the repository; only installed
applications belong in the runtime descriptor registry.

Start RRM Global, RRM Local and your launch interface as described in
[HowToStart](../HowToStart.md). Select the registered application, configuration,
target node(s) and user parameters. The framework invokes
`framework/core/rrm_local/app_starter/AppStarter.py`; the generated class is not
a standalone command-line program.

Optional desktop GUI presets belong in
`framework/applications/<application name>/gui_config/*.json`.
For example, a BreathAnalysis preset can contain:

```json
{
  "name": "Three IMUs - local MQTT",
  "description": "Thorax, abdomen and reference sensors with MQTT output",
  "userargs": {
    "imunames": "IMU_A-IMU_B-IMU_C",
    "peripheral_locations": "thorax-abdomen-reference",
    "adapter": "hci0",
    "campaignname": "demo",
    "samplingfreq": "10",
    "method_output": "DB",
    "path_FILE": "output/",
    "host_DB": "localhost",
    "port_DB": "1883"
  }
}
```

Replace placeholder IDs with registered, reachable sensors. IDs and locations
use `-` as a separator and must appear in the same order. Current online
BreathAnalysis requires three locations: `thorax`, `abdomen` and `reference`.
Use the desktop GUI's configuration-loading controls to apply a preset.
The WebApp has separate maintenance screens; follow [HowToStart](../HowToStart.md).

BreathAnalysis uses the updated BLE manager in RAW mode because its quaternion pipeline needs individual samples. Acquisition mode is fixed internally by
`RAW_ACQUISITION = True`, and the acquisition topic by
`MQTT_TOPIC_RAW = "aaac/campaign/imu"`.

## 9. Send notifications to the user and report peripheral usage

Application notifications use the framework interface injected by
`set_framework`: call `self._app.notify_message(message, severity="info")`
from your task methods. No extra imports, MQTT connection or descriptor
parameters are needed.

### Send a textual notification

```python
# Inside an application's setup, loop or cleanup method:
self._app.notify_message("Acquisition is ready")
self._app.notify_message("Battery level is low", severity="warning")
self._app.notify_message("The IMU connection failed", severity="error")
```

Use `info` for ordinary events, `warning` for situations requiring attention,
and `error` for failures. Supply a non-empty message. The default severity is
`info`; use the three names above so clients can display the appropriate style.
Include useful context such as the sensor ID and campaign, but not credentials or other sensitive data.

The message travels from the application through RRM Local and RRM Global to connected GUI clients. Connect your launch interface to RRM Global first; see [HowToStart](../HowToStart.md). The desktop GUI displays these messages as
information, warning or error dialogs. Other clients, including the WebApp,
must implement handling for framework notifications to display them.
`print()` and Python logging do not send this kind of GUI notification.

### Add notifications to a generated task

For the `WindowDemo` application from sections 3–5, you can replace these setup and processing methods with the following versions. The descriptor and output
keys stay unchanged:

```python
def Acquire_setup(self):
    self._next_sample = 0
    self._app.notify_message("WindowDemo: synthetic acquisition is ready")
    return True

def Processing_setup(self):
    self._above_threshold = False
    return True

def Processing_loop(self, window):
    result = sum(window) / len(window)
    # Example threshold only: replace it with a meaningful algorithm event.
    above_threshold = result >= 50
    if above_threshold and not self._above_threshold:
        self._app.notify_message(
            f"WindowDemo: mean crossed the demo threshold (mean={result:.2f})",
            severity="warning",
        )
    self._above_threshold = above_threshold
    return {"result": result}
```

Notify on significant events or state changes, not on every sample or window:
frequent messages can flood the interface with dialogs. The flag above sends
one warning when the threshold is crossed, and allows another only after the
value has dropped below the threshold and crossed it again. In a distributed
application, send an event from its owning task to avoid duplicate messages
from several partitions.

Notifications are side effects: keep returning the dictionary required by the
task graph. An `error` notification does not raise an exception or stop the
application. For a fatal failure, notify and then propagate the exception, or
call `self._app.stop_application()` when an intentional stop is appropriate.
Keep cleanup responsible for closing connections and releasing resources.

For a real example, see
[Battery_BLE](../framework/applications/Battery_BLE/Battery_BLE.py): it formats
battery readings into a message, calls `notify_message` then explicitly asks the framework to stop the application.

### Report peripheral usage separately

Text notifications do not update sensor usage. Use the dedicated methods in
the acquisition task, with the IDs registered in the framework (not merely
custom packet aliases):

```python
# After the acquisition manager has successfully connected in task setup:
self._app.notify_peripherals_in_use(["IMU_A", "IMU_B"], "ble")

# Later, in task cleanup, after disconnecting those peripherals:
self._app.notify_peripherals_released(["IMU_A", "IMU_B"])
```

Use `"wifi"` instead of `"ble"` for Wi-Fi acquisition. Pass a list of individual
IDs, not one string containing delimiter-separated IDs. 

These methods wrap `send_status` with the correct payloads. For reference, the equivalent low-level calls are:

```python
self._app.send_status({
    "in_use": [{"id": "IMU_A", "connection_type": "ble"}]
})
self._app.send_status({"released": ["IMU_A"]})
```


BLE GATT notifications received by a manager are a separate concept: use the existing acquisition manager for those, and `notify_message` for user-facing framework messages.

## Integration checklist

- Validate descriptors; keep task IDs, method names and data keys aligned.
- Generate into a new directory; preserve implemented code when changing descriptors.
- Include application helpers and dependencies on every execution node.
- Choose RAW or FEATURES based on the algorithm's input; prefer Wi-Fi for high
  transmission frequencies and BLE for low ones.
- Bound queue reads, handle missing data, and release resources in cleanup.
- Test on one local node before splitting tasks across partitions.
- Separate acquisition and result publishing, and verify downstream ingestion.

For additional details, consult [framework/README.md](../framework/README.md).
